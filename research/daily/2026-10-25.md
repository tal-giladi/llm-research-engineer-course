### C-20261025-01 · TorchTitan Update: New SOTA Models, Performance at Scale, TitanRL

- **Class:** A
- **Date discovered:** 2026-10-25
- **Date published:** 2026-10-21/22 2026 (PyTorch blog lists it under "October 21, 2026" on the blog index; the post's own page header shows "Last updated: 2026-10-22")
- **Source:** https://pytorch.org/blog/torchtitan-update-new-sota-models-performance-at-scale-titanrl/ (verified resolves; PyTorch's own official engineering blog, confirmed present on the live pytorch.org/blog index at the dates above)
- **Organization/researchers:** The TorchTitan team (PyTorch/Meta); co-credits a community study at https://yichuan-w.github.io/blog/GDN-train-inference-mismatch-asyncRL/ for the batch-invariant-mode numerical-mismatch analysis.
- **Category:** distributed/efficient training (training framework update: RL training infra, sharding, checkpointing, MoE communication)
- **What changed:** TorchTitan (PyTorch's native pretraining/post-training framework, already the closest production analogue to the course's from-scratch Module 09 distributed-training material) shipped a bundle of changes across four areas: (1) **TitanRL** — RL training is now first-class inside TorchTitan, using the *same* model definition from pretraining through post-training and inside vLLM (rather than separate training/inference model copies that can silently drift), with an opt-in **batch-invariant mode** that makes the trainer and generator produce bitwise-identical log-probabilities in supported on-policy configurations; (2) **FlexShard** — a new sharding library (beyond FSDP2) with `Owned`/`BlockShard` placements that lets the distributed Muon optimizer run without an extra All-Gather, and lets FP8-quantized parameter all-gathers skip extra scaling-factor collectives; (3) **Dist-MoE** — a newly open-sourced distributed-MoE communication library (fused token routing + expert compute over symmetric memory) with DeepSeek-V3 Blackwell recipes; (4) **torch_checkpointing** — a new distributed-checkpoint library that removes DCPv1's per-save synchronization barrier.
- **Technical summary:** Concrete, hardware-measured numbers reported in the post itself (not a third party): FlexShard's distributed-Muon support improves DeepSeek-V3 optimizer-step time by up to 79% vs. an FSDP-only implementation on 256 H100s; FlexShard's blockwise-quantized FP8 all-gather improves Llama-3 405B end-to-end step time by up to 20% on 256 H100s by cutting all-gather communication volume ~50%; `torch_checkpointing` on 512 H100s training DeepSeek-V3 671B cuts average trainer-blocking time from 841.2ms to 34.1ms and average checkpoint-write time from 384.4s to 13.1s. A DeepSeek-V3 671B+MTP1 MLPerf-style run on an internal GB300 cluster (256–512 GPUs, PP/VPP/DP/EP combinations, MXFP8) is reported to match Megatron's loss-convergence curve. TitanRL is reported stable for "hundreds of steps" on MoE and dense models on long-context/code-execution/self-play agentic tasks (SWE-ReBench, Terminal-Bench 2.1, Qwen3.5-35B-A3B at 64K–128K context on 40/20 GB300s) — training-curve figures only, no held-out accuracy table in the post. TorchTitan is also now a selectable training backend inside verl, Miles, and (as the design inspiration for its training engine) AReaL.
- **Why it might matter:** This is adoption evidence for several mechanisms already taught or referenced in the course, not a speculative single paper: (a) it directly extends the already-accepted Muon lesson (`lessons/module-03/lesson-04.md`, `research/accepted/muon-optimizer.md`) with a concrete distributed-systems result (what it costs to shard Muon's orthogonalized update across GPUs, and a library built specifically to make that cheap); (b) it is the first primary-source material the registry has seen for the "same model, pretraining through RL through serving" design point that TitanRL's batch-invariant mode targets — directly relevant to any lesson on RL/RLVR training-serving mismatch; (c) it is official, dated, concrete evidence (not a claim) for a widely-used open-source framework, satisfying the protocol's "adoption, not news" bar for OSS releases more cleanly than most daily arXiv findings do.
- **Evidence of adoption:** Strong for an OSS release: this is TorchTitan's own official update post, and the post itself names three other frameworks now using TorchTitan as a training backend (verl, Miles) or design inspiration (AReaL's Archon engine) — independent, verifiable adoption beyond the authoring team, plus FlexShard/Dist-MoE are separately open-sourced libraries (https://github.com/meta-pytorch/flex_shard, Dist-MoE referenced in-post) rather than only in-repo code.
- **Major organizations using it:** PyTorch/Meta (originator); adopted as a training backend by the verl and Miles projects; design-inspiration credit from the AReaL project. No frontier-lab production-training confirmation beyond Meta's own internal GB300-cluster benchmark runs described in the post.
- **Open-source implementation:** https://github.com/pytorch/torchtitan (verified exists, the subject framework itself); https://github.com/meta-pytorch/flex_shard (FlexShard, linked from the post)
- **Paper:** none (engineering blog post, not a paper)

- **Relationship to existing course material:** Directly extends `lessons/module-09/lesson-01.md`–`lesson-03.md` (data/FSDP/pipeline/tensor parallelism) and `research/accepted/muon-optimizer.md` / `lessons/module-03/lesson-04.md` (Muon). ### C-20261025-02 · A Quadratic Lens on Muon's Polar Update: Benefits, Pitfalls, and the Role of Newton-Schulz

- **Class:** B
- **Date discovered:** 2026-10-25
- **Date published:** 2026-10-21 (v1)
- **Source:** https://arxiv.org/abs/2610.30280 (verified resolves; v1, Wed 21 Oct 2026 18:01:04 UTC, cs.LG; comments: "47 pages, 13 figures. A shorter version was presented at the ICML 2026 Workshop on High-dimensional Learning Dynamics")
- **Organization/researchers:** Egor Shulgin, Sam Laing, Antonio Orvieto, Peter Richtárik (affiliations not stated on the abstract page; Richtárik is an established convex-optimization researcher, Orvieto an established deep-learning-dynamics researcher — general knowledge, not independently re-confirmed here).
- **Category:** training/optimization (theoretical analysis of the Muon optimizer's orthogonalized update, already taught in lesson 03.4)
- **What changed:** The course already teaches Muon (`lessons/module-03/lesson-04.md`, `research/accepted/muon-optimizer.md`) as orthogonalized momentum approximated by a few Newton-Schulz iterations, without a from-first-principles account of *when* orthogonalizing the update helps vs. hurts, or why using an *approximate* (few-iteration) orthogonalization can beat exact orthogonalization. This paper analyzes PolarGD (Muon's core update) on matrix quadratics — a setting solvable in closed form — to answer both questions directly.
- **Technical summary:** Per the paper (full abstract not independently reproduced here due to a 125-character quoting limit on the fetch tool, but corroborated by the comments field and summary): orthogonalization helps when the gradient is far from low-rank with high curvature along its largest singular directions; PolarGD can reach the minimizer in one step under conditions gradient descent cannot match; PolarGD is rotation-invariant (unlike plain sign descent); and, over many steps, PolarGD behaves like gradient descent preconditioned by the current iterate, so tiny singular values of the iterate slow it down relative to gradient descent — exactly the regime where Muon's incomplete (few-iteration) Newton-Schulz approximation, which handles tiny singular values more like gradient descent than true orthogonalization does, converges *faster* than exact orthogonalization would. The authors report that in a transformer actually trained with Muon, about a quarter of attention-matrix singular values fall in this tiny-singular-value regime — i.e., the pitfall is not merely theoretical for the exact architecture type the course teaches.
- **Why it might matter:** This is not a new technique but a from-first-principles explanation of *why* the course's already-taught Muon approximation (a handful of Newton-Schulz iterations rather than exact orthogonalization) is not just "good enough" but can be the better choice — exactly the kind of mechanism the course's "implement from scratch, then explain what the production version does and why" rule wants for 03.4. The empirical check against a transformer's own attention-matrix singular-value spectrum (not just synthetic quadratics) is a concrete bridge from the closed-form theory to the architecture already in `code/src/llmre/optim/muon.py`.
- **Evidence of adoption:** A shorter version was presented at an ICML 2026 workshop (peer-reviewed workshop acceptance, not a main-conference track) — a real but modest evidentiary upgrade over a bare, unreviewed preprint; no code release, no third-party reproduction of the attention-matrix singular-value measurement found.
- **Major organizations using it:** None identified; academic authorship, no stated lab affiliation.
- **Open-source implementation:** none found on the abstract page.
- **Paper:** https://arxiv.org/abs/2610.30280
- **Code:** none found
- **Relationship to existing course material:** Directly extends already-taught material: `lessons/module-03/lesson-04.md` (03.4, Muon) and `code/src/llmre/optim/muon.py`, plus `research/accepted/muon-optimizer.md`. Checked via `lookup "Muon optimizer"` and `lookup "Newton-Schulz polar"` (both surface only the existing accepted lesson/code, confirming this specific quadratic-lens/singular-value analysis is new, not a duplicate).
- **Potential course lesson:** If independently reproduced (or at least cross-checked against the course's own `muon.py` on a toy quadratic), a short theory addendum to 03.4: why the few-iteration Newton-Schulz approximation is not merely cheaper than exact orthogonalization but, in the tiny-singular-value regime that a quarter of real attention matrices sit in, measurably better.
- **Confidence:** medium — credible, named authorship, a real closed-form theoretical analysis (not just an empirical ablation) plus one concrete empirical check against a real transformer's weights, and a workshop (not main-track) peer review; no code, no independent reproduction of the empirical claim.
- **Recommendation:** monitor; worth an early look given it bears on already-taught from-scratch code (03.4/`muon.py`) rather than opening new scope — revisit if the full paper's empirical section (not yet fetched beyond the summary) holds up or if a main-conference version appears.

### C-20261025-03 · SPARE: Sparsity Allocation via Routing Entropy for Efficient MoEs

- **Class:** B
- **Date discovered:** 2026-10-25
- **Date published:** 2026-10-21 (v1)
- **Source:** https://arxiv.org/abs/2610.29662 (verified resolves; v1, Wed 21 Oct 2026 12:40:00 UTC, cs.LG primary, cross-listed cs.CL)
- **Organization/researchers:** Yifan Yang, Hanling Yi, Dongquan Yang, Feng Lin, Rong Xiao, Aijun Li, Xiaotian Yu (affiliations not stated on the abstract page).
- **Category:** efficiency (training-free expert pruning for Mixture-of-Experts models)
- **What changed:** The course teaches MoE architecture (`lessons/module-12/lesson-04.md`, DeepSeek-style) and expert-parallel sharding (`lessons/module-09/lesson-03.md`), but has no lesson on MoE *compression for deployment* — pruning experts to shrink the memory footprint. Existing expert-pruning work mostly decides *which* experts to remove per layer while pruning every layer by the same fixed ratio. SPARE instead sets *how many* experts to remove *per layer*, based on that layer's routing entropy (measured from normalized top-K gate weights on calibration data): layers whose routing is more diffuse (higher entropy) are pruned more aggressively, since removing an active expert there discards less gate weight.
- **Technical summary:** Training-free, selector-agnostic (works with any "which expert to drop" method) — the contribution is the per-layer *budget* allocation. The authors support the entropy-based allocation with a perturbation bound under random pruning and a controlled intervention showing concentrated routing produces larger output changes when pruned. With the same selector and total pruning budget, SPARE reportedly beats uniform (equal-ratio-per-layer) allocation on Mixtral, Qwen3, and DeepSeek-family models, with the gap widening at high pruning ratios; at 50% expert pruning, Qwen3-30B-A3B's eight-task average is reported to rise from 57.2% to 63.8%, and DeepSeek-R1's math/code/science average from 80.1 to 82.8 (both vs. uniform allocation at the same budget, per the abstract/summary — full paper not fetched, no code repository found on the abstract page).
- **Why it might matter:** A training-free technique with a stated theoretical justification (not just an empirical trick), tested across three different open MoE model families including one the course already references (DeepSeek), for a deployment problem (MoE memory footprint) the course currently has zero coverage of.
- **Evidence of adoption:** None — single paper, four days old at discovery, no stated venue, no code release found, no third-party reproduction.
- **Major organizations using it:** None identified (no stated affiliation); evaluated against open models (Mixtral, Qwen3, DeepSeek) rather than the authors' own model, which aids future reproducibility.
- **Open-source implementation:** none found on the abstract page.
- **Paper:** https://arxiv.org/abs/2610.29662
- **Code:** none found
- **Relationship to existing course material:** New topic — no existing accepted/deferred registry entry for MoE compression/expert pruning (checked via `lookup "expert pruning MoE compression"` and `lookup "mixture of experts routing"`, surfacing only the existing MoE architecture lesson and an unrelated staging match). Bears on `lessons/module-12/lesson-04.md` and `code/src/llmre/model/moe.py` as a deployment-time extension.
- **Potential course lesson:** If independently reproduced or adopted, a short deployment-focused addendum to 12.4 (or a new efficiency-module entry): "pruning MoE experts non-uniformly by routing entropy," using the Qwen3-30B-A3B/DeepSeek-R1 numbers as the motivating example.
- **Confidence:** low-medium — concrete numbers across three real model families and a theoretical (not just empirical) justification, but one paper, no stated venue, no code, no independent reproduction.
- **Recommendation:** monitor; revisit if code is released or a second group reproduces the entropy-based allocation advantage over uniform pruning.
