### C-20261113-01 · Independent 1T-parameter MoE pretraining on TorchTitan (EUROPA consortium on JUPITER): whole-expert FlexShard ownership for Muon, Newton-Schulz on GPU with CPU-offloaded params, activation-checkpoint offload to Grace, FSDP stream-pool fragmentation fix

- **Class:** A
- **Date discovered:** 2026-11-13
- **Date published:** 2026-11-12
- **Source:** https://pytorch.org/blog/training-a-1t-parameter-moe-on-eu-public-infrastructure-with-pytorch-and-torchtitan/ (verified, HTTP 200). Companion full write-up https://www.domyn.com/blog/training-1t-moe-eu-public-infrastructure-pytorch **not fetched** (host outside this session's allowed network domains).
- **Organization/researchers:** EUROPA consortium (Domyn, Fraunhofer IAIS and IIS), EuroHPC Frontier AI Grand Challenge; posted on the PyTorch blog.
- **Category:** distributed
- **What changed:** The deferred topic `flexshard-distributed-muon-sharding.md` (WAIT since 2026-10-25) named "independent use or measurement outside the TorchTitan team" as what would change the decision. This is that: a non-PyTorch team pretraining a 951.9B-total / 32.8B-active MoE (74 layers, 384 routed experts top-8, 65,536-token sequences, Muon for ~99.5% of parameters + AdamW for router/embeddings) on 384 GH200 per DP replica (1,536 GPUs, 4 replicas) uses FlexShard's whole-parameter ownership so each rank holds complete expert matrices and runs Newton-Schulz with no communication; dense matrices are gathered to an owning rank and overlapped with expert work.
- **Technical summary:** Authors' numbers (consortium claim): throughput 90 -> ~1,300 tokens/s per GPU in stages. Layout: 384-way FSDP, 4-way EP inside a node (all-to-all kept on NVLink), no PP, ~25M tokens/step. (1) Muon needs one fp32 state vs Adam's two, which is what lets 65K-token sequences fit. (2) With FSDP CPU offload, Newton-Schulz on the 72 Grace cores took ~35 s/step; staging it on the GPU while params stay offloaded (merged TorchTitan PR #5352) cut the optimizer step 41.7 s -> 2.2 s, 441 -> 597 tok/s/GPU. (3) Full activation checkpointing (store only layer-boundary activations) took 90 -> 370 tok/s since the GPU was idle anyway; boundary activations at 65K tokens are 74 x 65,536 x 6,144 x 2 B ~ 55 GiB, so they are offloaded to Grace over NVLink-C2C and prefetched one layer early: 370 -> 508 tok/s. (4) The CUDA caching allocator keeps one pool per stream; FSDP's side streams held 27.3 GiB of which 6.4 GiB live, starving the compute stream; running the all-gather setup on the compute stream (`unshard_async_op`, now public as `set_unshard_in_current_stream`, PyTorch PR #202343, merged 6 Nov) cut peak reserved 88.1 -> 74.6 GiB and took 996 -> 1,210 tok/s. Fixes upstreamed to TorchTitan/PyTorch.
- **Why it might matter:** Every step is a back-of-envelope calculation the course already teaches the ingredients for (03.4 Muon state and Newton-Schulz cost; 09.2 FSDP all-gather/compute overlap; 09.3 EP/parallelism layout; 08.x memory arithmetic), so it is a dated, numerically rich real-world case study: why the optimizer-state count decides max sequence length, why an optimizer that needs whole matrices conflicts with FSDP's row sharding and how whole-expert ownership removes the conflict, why recomputation is free when the GPU is communication-bound, and the per-stream allocator pool as a non-obvious memory failure mode. Teachable at CPU scale as arithmetic plus a small placement simulation.
- **Evidence of adoption:** FlexShard is in TorchTitan main (README verified); PR #5352 merged 2026-10-26 (verified); PyTorch PR #202343 merged 2026-11-06 (verified). The earlier evidence (TitanRL post) was from the TorchTitan team; this is a second, independent team using it at 1T scale (consortium claim; no independent reproduction of the throughput numbers).
- **Major organizations using it:** PyTorch/TorchTitan (Meta-led), Domyn, Fraunhofer IAIS/IIS, Jülich Supercomputing Centre (host); Megatron Core has its own layer-wise distributed Muon (already cited in `accepted/muon-optimizer.md`).
- **Open-source implementation:** https://github.com/pytorch/torchtitan/blob/main/torchtitan/distributed/flex_shard/README.md (verified); https://github.com/pytorch/torchtitan/pull/5352 (verified, merged); https://github.com/pytorch/pytorch/pull/202343 (verified, merged)
- **Paper:** none (engineering blog post)
- **Code:** see open-source implementation; the model itself is not released.
- **Relationship to existing course material:** `deferred/flexshard-distributed-muon-sharding.md` (this meets its stated re-review trigger); `accepted/muon-optimizer.md` (lesson 03.4, section 6 covers layer-wise distributed Newton-Schulz); lessons `lessons/module-09/lesson-02.md` (ZeRO/FSDP) and `lessons/module-09/lesson-03.md` (parallelism; mentions offload once). No registry file for activation offloading or allocator stream pools.
- **Potential course lesson:** Extension to 09.2 (not a new lesson): "Optimizer-aware sharding and memory at 1T scale" — (a) Muon vs Adam state bytes -> max sequence length arithmetic, (b) row-shard vs whole-parameter (Owned) placement for Newton-Schulz with a toy CPU simulation of communication bytes, (c) activation-checkpoint offload arithmetic (the 55 GiB computation), (d) a common-mistakes callout on per-stream caching-allocator pools. ### C-20261113-02 · Stochastic rounding of FP32 master weights to BF16 closes the BF16-vs-FP16 convergence gap in low-learning-rate RLVR ("weight sticking")

- **Class:** B
- **Date discovered:** 2026-11-13
- **Date published:** 2026-11-10 (v1)
- **Source:** https://arxiv.org/abs/2611.13545 (verified, HTTP 200)
- **Organization/researchers:** Mahdi Nazemi, Oleg Rybakov, Tijmen Blankevoort, Asit Mishra, Carlo del Mundo (affiliations not shown on the abstract page).
- **Category:** RL/post-training
- **What changed:** Authors report that at the low learning rates typical of RLVR, BF16 mixed-precision training converges more slowly than FP16 at the same LR. Mechanism: round-to-nearest from FP32 shadow weights to BF16 swallows small updates (BF16 has 8 mantissa bits), so the BF16 copy used in the forward pass does not move for several steps ("weight sticking"). Raising the BF16 LR closes the gap but increases KL to the reference. Stochastic rounding of the FP32 -> BF16 conversion matches FP16 convergence speed, with lower KL than the high-LR BF16 run, keeping BF16's range and needing no loss scaling.
- **Technical summary:** Paper claims only (abstract read; no numbers in the abstract; no code linked). The argument is a direct numerical consequence of BF16's precision: an update `lr * g` smaller than half a BF16 ulp of the weight rounds away; stochastic rounding makes the rounded value unbiased in expectation, so small updates take effect on average.
- **Why it might matter:** A clean, CPU-demonstrable numerics point that connects two existing lessons: 08.3 (bf16 vs fp16 bit layouts, "bf16 needs no loss scaling") and 16.4 (training-inference mismatch, where FP16 has been discussed as a fix). The weight-sticking computation is a perfect "tiny numbers by hand" example (weight 1.0, BF16 ulp 2^-7, update 1e-3 -> lost). It also gives a second reason, besides mismatch, why RL runs care about precision.
- **Evidence of adoption:** none; single paper, three days old, no code. Stochastic rounding itself is an established technique (e.g. used in low-precision training literature), but its application here is not independently validated.
- **Major organizations using it:** none known.
- **Open-source implementation:** none
- **Paper:** https://arxiv.org/abs/2611.13545
- **Code:** none
- **Relationship to existing course material:** `lessons/module-08/lesson-03.md` (mixed precision; no mention of stochastic rounding in lessons); `accepted/rl-training-inference-mismatch.md` (16.4); `deferred/rl-mismatch-rounding-location-alignment.md` (another BF16-rounding-in-RL topic). `lookup "stochastic rounding"` finds no topic file.
- **Potential course lesson:** none on its own. If code or replication appears: a worked "weight sticking" example and common-mistakes note in 08.3 (with a 10-line CPU demo of round-to-nearest vs stochastic rounding of FP32 -> BF16), cross-referenced from 16.4.
- **Confidence:** low (single paper; abstract-level claims; no code)
- **Recommendation:** monitor; the weekly review may fold it into `rl-mismatch-rounding-location-alignment.md` as a related BF16-numerics-in-RL topic. Re-judge on code release or independent confirmation.
