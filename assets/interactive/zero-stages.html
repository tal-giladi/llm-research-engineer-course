ZeRO: stop storing the same thing four times

Four GPUs train the same model on different batches. Follow one training step to see what each GPU keeps, temporarily borrows, and sends. Start with DDP, then compare the three ZeRO stages.

Toy model: layers A → B. Each layer has four equal parameter shards: A0…A3 and B0…B3. When sharded, GPU 0 owns A0 & B0, GPU 1 owns A1 & B1, and so on. Matching P, G, and O tiles refer to the same parameters. Tiles show ownership, not byte sizes.

Why these stages save memory

Example: 1 billion parameters, 4 GPUs, mixed-precision Adam. Per parameter: P = 2 bytes, G = 2 bytes, O = 12 bytes (FP32 master weight + Adam m + Adam v).

These are idealized model-state budgets per GPU, with gradient storage included—not live or peak GPU memory. Activations, temporary gathered parameters, communication buffers, padding, and allocator overhead are excluded. Actual precision and implementation choices can change these figures.

What exactly happens to the numbers?

Suppose the four GPUs compute gradient values 1, 3, 5, and 7 for the same parameter A0. Their average is 4.

All-reduce: all four GPUs receive 4. Reduce-scatter: the same averaging happens, but only A0's owner keeps its result 4; the other owners keep results for their own shards. No batch's contribution is discarded.

GPU 0 uses that averaged gradient and its local Adam state to update A0. In stages 1 and 2, the updated parameter is distributed to all GPUs. In stage 3, its owner keeps it until the layer is gathered for computation. All-gather copies shards; it does not average them.

Simplifications and what ZeRO does not do

Every GPU executes both layers on its own batch in every stage. ZeRO partitions model state; this is not pipeline parallelism with one layer assigned to each GPU.

This walkthrough serializes compute and communication to make them visible. Real implementations use buckets, overlap communication, and may prefetch or retain gathered parameters. A shard can cross tensor or layer boundaries. Stage 1 is illustrated with full gradient all-reduce; equivalent reduction schedules are possible. Stages 2 and 3 discard non-owned gradient results as buckets are reduced, so they do not need to retain a full model's gradients.

Here, each stage-3 layer is gathered again for backward and released after use. Actual release and reuse policies vary. ZeRO does not remove the need to store or recompute activations; activation checkpointing is separate. CPU/NVMe offload is not shown.
